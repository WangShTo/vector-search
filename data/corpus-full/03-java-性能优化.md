# Java 性能优化笔记

## 微基准测试的重要性

随手写的性能测试几乎没有参考价值。原因有很多：虚拟机需要预热才能把热点代码
编译成机器码，前几千次调用测出来的其实是解释执行的速度；
即时编译器会做死代码消除，如果计算结果没有被使用，整段计算可能被直接删掉；
循环里重复计算同一组数据，分支预测和缓存都会给出过于乐观的结果。

JMH 是官方的微基准框架，它通过多轮预热、多轮测量、以及在全新的虚拟机进程中
运行每个测试组合来解决这些问题。它还提供了 Blackhole 机制来消费计算结果，
防止死代码消除。

一个容易被误解的行为是：JMH 为每一个参数组合都启动一个全新的虚拟机进程。
这样做是为了防止不同参数组合之间通过即时编译状态和堆布局互相污染。
后果是静态字段无法跨参数组合共享 —— 如果每个参数组合都需要构建一份昂贵的数据，
总耗时会按参数个数成倍增长。

## 堆内与堆外内存

Java 对象有对象头，一个 float 数组除了数据本身还要额外承担十几字节的头部开销，
再加上引用它的指针。存放千万级向量时，这些开销会累积到相当可观的程度。

更严重的问题是垃圾回收。大数组会直接进入老年代，频繁的回收会造成明显的停顿。
把这类生命周期长、体积大的数据放到堆外内存，可以让垃圾回收器完全不用管它们。
代价是需要自己管理内存的分配与释放，代码复杂度上升。

Java 新版本提供了外部函数与内存接口，可以用比过去的直接缓冲区更安全的方式
操作堆外内存。

## 缓存友好性

现代处理器的内存访问以缓存行为单位，通常是六十四字节。
如果数据在内存中是连续存放的，一次缓存行加载就能拿到多个有用的值。
如果数据是通过指针散落各处的，每次访问都可能触发一次缓存缺失。

链表与数组的经典对比就是这个道理的体现。在向量检索里，
图结构如果每个节点用独立的对象表示，邻居列表用独立的数组表示，
那么遍历邻居时会发生大量的指针跳转。改成把所有节点的向量拼成一个大数组、
把所有边拼成一个大数组，用下标而不是引用去访问，能显著改善缓存命中率。

## 伪共享

多个线程修改位于同一个缓存行上的不同变量时，会发生伪共享。
虽然逻辑上没有冲突，但处理器为了保证缓存一致性，会让这个缓存行在核心之间
反复失效和同步，性能可能下降一个数量级。

解决办法是让这些变量之间留出填充，保证它们落在不同的缓存行上。
Java 提供了相应的注解来自动完成这件事。

## 锁的选择

读多写少的场景适合使用读写锁。它允许多个读线程同时进入，只在写的时候独占。

读写锁还有进一步优化的空间。乐观读策略假设读的时候不会有写入发生，
先不加锁地读取版本号，读完再检查版本号有没有变。如果没有变，
这次读操作完全不需要加锁；如果变了，再退化成加锁重读。
在读操作占绝大多数、且读操作本身很短的场景下，这个策略能显著提升吞吐。

## 用数据说话

性能优化最忌讳凭感觉猜瓶颈。正确的做法是先把耗时拆开，
定位到真正的热点，再动手改，改完用同样的方法量一遍。

记录每一阶段的耗时并暴露出来，是一个成本很低但收益很高的工程习惯。
它让「瓶颈在哪」这个问题不再需要争论。

反过来，如果没有基线数据，任何「提升了多少倍」的说法都是空的。
所以每做一项优化，都要保留优化前的版本作为对照组。
