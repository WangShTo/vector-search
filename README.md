# 自研向量检索服务（Java 引擎 + Python 模型服务）

从零实现的语义检索服务：**Java 侧自研 HNSW 索引引擎**负责存储与检索，**Python 侧**提供 embedding / rerank 模型服务。不依赖 Faiss、Milvus、Elasticsearch 等任何现成向量检索库。

> 目标不是"跑通一个 RAG demo"，而是**把检索系统的每一步都做成可测量、可对比、可解释的工程决策**。

## 这个项目在做什么

语义检索要解决的核心矛盾是：**在百万级文档里，用毫秒级延迟，找到语义最相关的几条。**

暴力遍历所有向量做内积，准确率 100%，但 O(n·d) 的复杂度在百万级数据上完全不可用。HNSW（Hierarchical Navigable Small World）用近似换速度：把向量组织成分层邻近图，用少量召回率损失换取数量级的延迟下降。

这个项目把这条链路完整实现了一遍，并且**每一步优化都保留可对比的基线**：

| 环节 | 基线 | 优化后 | 验证方式 |
|---|---|---|---|
| 检索结构 | 暴力遍历 | HNSW 分层图 | recall@10 对照暴力检索 |
| 距离计算 | 标量循环 | JDK Vector API (SIMD) | JMH 微基准 |
| 向量存储 | `List<float[]>` 堆内 | 堆外内存（计划中） | 堆占用与 GC 停顿 |
| 跨进程调用 | 逐条 embedding | 批量 + 动态批处理 | 端到端 P95 延迟 |
| 并发读 | `ReentrantReadWriteLock` | `StampedLock` 乐观读（计划中） | 压测 QPS / P99 |

**关键点：没有基线就没有优化。** 所有"提升 N 倍"的结论，都能在这个仓库里找到对照组。

   eval/evaluate.py       │                                                │

**为什么索引在 Java、模型在 Python？** 这是刻意的职责切分。模型推理生态在 Python 无可替代；而索引引擎需要的是内存布局控制、并发原语、JIT 优化——那正是 Java 的强项。两者的边界（跨进程批量调用）本身就是本项目最重要的性能优化对象。

### 方式一：一键启动（推荐）

仓库自带开发脚本，一条命令拉起两个服务并等到就绪：

```powershell
# 首次需要装 Python 依赖
cd model-service
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
cd ..

# 启动（后台运行，日志写到 logs/）
.\scripts\dev.ps1 start

# 查看状态与索引统计
.\scripts\dev.ps1 status

# 停止
.\scripts\dev.ps1 stop
```

`dev.ps1` 还提供三个常用动作：

| 动作 | 作用 |
|---|---|
| `load` | 把 `data/eval/corpus.jsonl` 灌进索引 |
| `smoke` | 端到端冒烟测试（真实 BGE + 语义检索验证） |
| `eval` | 跑检索质量评测，输出 recall / MRR / NDCG / 延迟报告 |

### 方式二：手动分别启动

```bash
# Python 模型服务（首次启动会下载 BGE 模型，约 100MB，之后走本地缓存）
cd model-service
.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000

# Java 检索服务
cd vector-search-java
mvn spring-boot:run
```

服务地址：Java `http://127.0.0.1:8080`，Python `http://127.0.0.1:8000`。

### 方式三：Docker Compose

```bash
docker compose up --build
```

## API 示例

### 批量灌入文档

```bash
curl -X POST http://localhost:8080/api/documents \
  -H "Content-Type: application/json" \
  -d '{
    "documents": [
      {"id": 1, "text": "HNSW 是一种基于分层可导航小世界图的近似最近邻算法。"},
      {"id": 2, "text": "BM25 是经典的稀疏检索算法，基于词频和逆文档频率。"}
    ]
  }'
```

### 检索

```bash
curl -X POST http://localhost:8080/api/search \
  -H "Content-Type: application/json" \
  -d '{"query": "分层图的近似最近邻", "topK": 5}'
```

响应里带**分阶段耗时**，这是定位瓶颈的关键：

```json
{
  "query": "分层图的近似最近邻",
  "hits": [{"id": 1, "score": 0.8731, "text": "HNSW 是一种..."}],
  "indexType": "hnsw",
  "timing": {"embeddingMs": 45, "searchMs": 2, "totalMs": 47}
}
```

> 如果 `embeddingMs` 远大于 `searchMs`，说明瓶颈在跨进程调用而不是索引本身——
> 这时候去调 HNSW 参数是南辕北辙。这个字段就是为了让这种误判不可能发生。

### 查看索引状态

```bash
curl http://localhost:8080/api/stats
```

返回 HNSW 的图结构指标（层高直方图、总边数）。**层高分布应该呈金字塔状衰减**，如果不是，说明建图参数或随机源有问题，recall 一定上不去。

### 落盘索引（重启后秒级恢复）

```bash
curl -X POST http://localhost:8080/api/admin/snapshot
```

返回快照文件路径、大小、向量数与耗时。

**为什么需要这一步**：10 万条数据建图要 **129 秒**，而快照恢复只要 **1 秒左右**。
不落盘的话每次重启都得等两分钟，这在演示和部署时是不可接受的。

落盘之后重启服务会自动从 `data/index/` 恢复，不需要重新灌数据。
要重新灌数据时，删掉该目录下的两个文件即可。

### 切换索引实现（做对照实验用）

```bash
curl -X POST "http://localhost:8080/api/admin/reset?type=brute-force"
```

> ⚠️ 会清空当前索引。这是刻意的：对照实验必须在同一份数据、干净的状态下重建，否则测出来的数字不可比。

## 设计取舍（面试弹药）

这一节记录**每个决策背后的理由和被否决的方案**。代码写对不难，能讲清"为什么这么选"才是区分度。

### 1. 为什么邻居选择要用启发式，而不是取最近的 M 个？

直接取最近的 M 个邻居，会让所有邻居聚在同一个方向，查询时容易一头扎进局部最优出不来。HNSW 论文的启发式加了多样性约束：只有当一个候选**距离查询点比距离任一已选邻居都更近**时才收它——直觉上是"这个邻居提供了别人提供不了的方向"。

不足 M 个时用被丢弃候选中最近的补齐（`keepPrunedConnections`），保证连通度。

### 2. 为什么 layer 0 的最大出边数是上层的两倍？

底层承载全部节点，需要更高连通度才能保证搜索不走进死胡同；上层节点数指数级减少，用 M 就够，也更省内存。这是内存与连通度的权衡。

### 3. 为什么 `efConstruction` 可以放心调大，`m` 不行？

`efConstruction` 只影响**建图时**的候选池大小，即一次性的构建成本，对查询延迟零影响。
`m` 决定了图的边数上限，一旦索引建好，改 `m` 就意味着必须重建整个索引。

**所以线上调优的策略是：`m` 一次性定好（16~48），把 `efSearch` 作为运行时可调的旋钮。**

### 4. 为什么查询向量要归一化，且用内积而不是余弦距离？

归一化后内积等价于余弦相似度，但省掉了每次比较时的两次开方和一次除法。在千万次比较的热点路径上，这个常数因子不可忽略。Python 侧 `normalize_embeddings=True` 和 Java 侧 `normalizedCopy` 是幂等的双重保险。

### 5. 为什么 embedding 接口设计成批量的？

Java 和 Python 是两个进程，每次调用都是一次完整的网络往返。灌 10 万条文档时，逐条调用就是 10 万次往返——HTTP 和 TCP 的开销会远超模型推理本身。批量接口把 N 次往返压缩成 1 次。

这也是为什么检索接口虽然只处理一条 query，却仍然走批量代码路径：**保持单一代码路径，避免"批量对了单条错了"这类只在某条路径上出现的 bug。**

### 6. 动态批处理为什么是单 worker？

动态批处理靠**进程内的共享队列**攒批。uvicorn 开多 worker 时每个进程各有一个队列，请求被打散，batch 永远攒不大——`/stats` 里的"平均批大小"长期接近 1 就是这个症状。

代价是单 worker 无法利用多核。当前的取舍是：**批处理带来的吞吐收益 > 多进程并行带来的收益**，因为模型推理是主要的 CPU 消耗方，而它已经吃满了。

### 7. 为什么 `SearchResult` 对外用相似度而不是距离？

HNSW 内部按"距离越小越近"排序，而归一化后的内积"越大越相似"。内部统一转换成距离语义做比较，对外统一用相似度。**两套方向混用是这类系统最容易埋下的 bug**，所以在类型层面就固定下来。

### 8. 为什么没有用堆外内存？

这是**评估后决定不做**的一个决策，理由比做本身更值得说。

堆外内存在这个场景下确实有吸引力：10 万条 512 维向量是 205 MB，
加上图结构后索引的堆内占用实测 278.6 MB。这些数组生命周期极长、
体积很大，正是垃圾回收最不喜欢的负载。

但 Java 21 上有一条硬约束：操作堆外内存的正规途径 `java.lang.foreign`
**仍是预览特性**，用它需要 `--enable-preview`，而预览 API 是**版本锁定**的 ——
升级一次 JDK 就得改一次代码。对一个要长期维护的项目来说，这个代价不小。

绕过它的方案是直接用 `ByteBuffer`，但那会引出第二个问题：
**Vector API 的 `FloatVector.fromArray` 只接受 `float[]`**，对堆外内存
只能用 `fromMemorySegment`（同样依赖预览 API）。如果坚持用 `ByteBuffer`，
距离计算就只能退回标量实现 —— 那会丢掉近 5 倍的 SIMD 收益，
而距离计算正是建图与查询的绝对热点。

**两边一权衡，结论很清楚**：在 Java 21 上，「扁平数组 + SIMD」的组合
明显优于「堆外内存 + 标量距离」。所以当前的选择是把数据放在堆内、
但保证它连续，等 JDK 22 之后 FFM 转正再重新评估。

这个判断还有一个副产品：它把问题从"要不要用堆外"变成了
"能不能让堆内数据连续" —— 而后者才是缓存友好性的真正来源。
最终的扁平化重构（约 30 万个对象降为 8 个数组）就是沿着这条路走的。

### 9. 为什么快照用两种格式（二进制 + JSONL）？

因为存的是两类性质完全不同的数据：

| 数据 | 格式 | 理由 |
|---|---|---|
| 向量 + 图结构 | **二进制**（`vector-index.snapshot`） | 定长数值，连续存储，读写都是大块 IO |
| 文档原文 | **JSONL**（`documents.jsonl`） | 变长 UTF-8 文本，二进制反而要自己处理长度前缀 |

**为什么向量不放 JSON**：浮点数文本化后会膨胀 3~4 倍（`0.1234567` 是 9 个字节，
二进制只要 4 个），20 万条 512 维向量会从 205 MB 涨到 700 MB 以上，
而且解析要经过字符串转换。这是"方便调试"换来"慢十倍"的典型亏本买卖。

**二进制快照的四个设计点**：

1. **魔数 + 版本号** —— 拿错文件立刻拒绝，而不是算出垃圾结果；格式演进时老文件能被识别
2. **每段独立 CRC32** —— 磁盘损坏或截断能被发现。**没有校验的话，损坏的索引会安静地
   返回错误结果**，这类 bug 几乎无法排查
3. **参数一致性校验** —— 段表里的长度必须与元数据推导的长度严格相等，
   不一致直接报错。这和小节 4 里那个"维度 768/512 写错"是同一类防御
4. **原子替换** —— 先写 `.tmp`、再 `ATOMIC_MOVE` 改名。中途崩溃不会留下半个文件
   被下次启动当成有效索引读进来

**还有一个来自扁平化的红利**：因为索引本来就是 7 个连续数组，
落盘就是"写 7 段字节"，读回就是"读 7 段字节"，没有任何对象图遍历或指针修正。
如果还是当初 `List<float[]>` + `List<int[][]>` 的对象化布局，序列化会痛苦得多。

**只写已用长度**：容量按 2 的幂增长（10 万节点时实际容量 131072），
按容量写会多存 31% 的空白字节。这里截断到 `nodeCount`，加载后需要扩容再重新增长。

### 10. 混合检索为什么用 RRF，而不是把分数加权相加？

**因为两种分数根本不可比。**

| 检索器 | 取值范围 | 含义 |
|---|---|---|
| 向量（余弦） | `[-1, 1]` | 语义相似度 |
| BM25 | `[0, +∞)` | 词频加权的匹配强度，**无上界** |

直接把两者相加，等于让 BM25 单方面决定结果 —— 它的分数动辄二三十，
而余弦最多 1.0。想先归一化也不行：两种分数的分布形状完全不同，
min-max 归一化会被个别极端值带偏。

**RRF 的做法是丢掉分数，只看排名**：

```
score(d) = Σ_i  1 / (k + rank_i(d))        k = 60
```

每路排第 1 的得 `1/(k+1)`，排第 5 的得 `1/(k+5)`。一篇文档若在两路都靠前，
分数自然叠加。这样做有三个好处：绕开了分数不可比、对异常分数免疫、
而且几乎没有需要调的参数。

**代价**是丢掉了分数里的置信度信息：排第 1 但分数 0.99 与排第 1 但分数 0.31，
在 RRF 里完全等价。想利用这个信息就得做分数校准，那是另一个话题。

**一个实测出来的反直觉结论**：等权 RRF 在**一路明显强于另一路**时会让混合变差 ——
弱的那路排第 1 的错结果会挤掉强的那路排第 11 的正确结果。
实测数据里，词面查询集上 BM25（0.96）远强于向量（0.80），
等权混合的结果（0.893）就落在了两者之间而不是之上。

但**跨两类查询看，混合仍然最好**：平均 0.8529（vs 0.8375 / 0.7925），
最差情况 0.8125（vs 0.80 / 0.625）。因为你无法预知用户会打哪种查询 ——
这才是生产上用混合检索的理由。详见 [`bench/REPORT.md`](bench/REPORT.md) 第六节。

### 11. 二阶段精排和向量检索有什么本质区别？

**一个是双塔，一个是单塔。**

| | 双塔（向量检索） | 单塔（cross-encoder 精排） |
|---|---|---|
| 结构 | 查询与文档**各自独立**编码成向量，再算内积 | 把（查询, 文档）**拼接**后一起送进模型 |
| 语义交互 | 无 —— 编码时两者没见过彼此 | 完整的注意力交互 |
| 能否预建索引 | 能（向量可离线算好） | **不能**（每个查询 × 每个候选都要跑一次前向） |
| 精度 | 较低 | 明显更高 |

所以两者不是替代关系，而是**分工**：向量检索负责从百万级里粗筛出几十条，
精排负责把这几十条排对。这就是「两阶段检索」。

实测（hybrid 模式，10 万级语料 602 分块）：

| 查询集 | 指标 | 精排前 | 精排后 |
|---|---|---|---|
| 词面 150 条 | recall@10 | 0.8933 | 0.8933（不变） |
| 词面 150 条 | MRR@10 | 0.6883 | **0.7523（+9%）** |
| 语义 16 条 | 命中率@10 | 0.8125 | 0.8125（不变） |
| 语义 16 条 | MRR@10 | 0.5568 | **0.6328（+14%）** |

**召回不变、排序变好**，这正是精排该有的表现。这也提供了一个自检手段：
如果精排让 recall 变了，说明第一阶段被改坏了 ——
指标之间要有明确分工，混在一起就失去了诊断能力。

代价是延迟从 43 ms 涨到 599 ms（CPU 上每个候选一次前向）。
所以 `rerank` 默认**关闭**，由调用方显式开启 ——
排序质量与延迟怎么权衡应该由业务场景决定，不该由框架替用户决定。

## 评测方法

评测集自己构建，因为通用中文数据集和你的语料领域不匹配，而"recall@10 达到 0.9"这句话只有在**你自己的语料和标注**上才有意义。

```bash
# 1. 把语料放进 data/corpus/（课程讲义、论文、笔记、代码都行）
# 2. 构建评测集
cd eval
python build_dataset.py --corpus-dir ../data/corpus --out ../data/eval --strategy paragraph

# 3. 灌入语料后跑评测
python evaluate.py --queries ../data/eval/queries.jsonl --top-k 10 --label hnsw-m16
```

### 评测协议：已知项检索

对语料里的一个分块，从它自己身上取一段文字当查询，正确答案就是它所在的文档。这样**不需要人工标注相关性**，但要求检索系统真的能把它找回来。

**必须说明的局限**：查询词与文档词高度重合，所以指标是**上界**，不等于线上效果。它适合做**相对比较**（改参数前后、两种索引之间、两种分块策略之间），不适合宣称绝对质量。报告模板里已经写明了这一点——不写清楚就是在误导人。

### 指标

| 指标 | 衡量什么 | 为什么不能只看它 |
|---|---|---|
| recall@k | 相关文档有没有进前 k | "全召回但排序很差"也能拿高分 |
| MRR@k | 第一个相关结果排在第几位 | 只看第一个，忽略其余 |
| NDCG@k | 位置加权的排序质量 | — |
| P50/P95/P99 延迟 | 长尾体验 | **平均值会掩盖长尾，线上体验由 P99 决定** |
