# 竞品对比：这个项目在同类里到底处于什么位置

写这一页不是为了证明"我们比别人强"，而是为了回答一个更实际的问题：
**如果面试官见过类似的仓库，我该怎么说明这个项目的差异在哪。**

所以下面分三层：哪些是真正的同类、逐项差多少、以及哪些差距我不想掩饰。

> 数据采集时间：2026-10-30，通过 GitHub Search API 与 `/repos/{owner}/{repo}` 元数据接口获取。
> 星数会变，结论（量级与定位）不会因为几百颗星的波动而改变。

---

## 一、先把"同类"分清楚

GitHub 上搜 `vector search` 会掉出几千个仓库，但它们是三种完全不同的东西：

| 层次 | 代表 | 规模 | 和本项目的关系 |
|---|---|---|---|
| **工业级向量索引库** | [jvector](https://github.com/jbellis/jvector) 1757★、[jelmerk/hnswlib](https://github.com/jelmerk/hnswlib) 304★ | 生产在用 | 能力上是我们的上限，但没有中文检索、没有混合召回 |
| **个人 / 学生级完整项目** | [Vectra-Core](https://github.com/DavidXander67/Vectra-Core) 64★ | 单人作品 | **最直接的参照物**，同样的定位、同样的量级 |
| **RAG 应用** | [ragent](https://github.com/nuwax-ai/ragent) 4402★、yu-ai-agent 2757★ | 团队项目 | **不是同类**：它们解决"怎么把模型接起来"，我们解决"索引本身怎么写" |

第三类星最多，但和本项目不构成竞争：那些仓库的核心是 prompt、Agent 编排、
前端交互，向量检索部分是调 Milvus / 向量数据库。我们恰好反过来。

**真正需要比的是第一类和第二类。**

---

## 二、与 Vectra-Core 逐项对比（最直接的参照）

Vectra-Core 是单人项目，HNSW + SQ8 量化 + 元数据过滤 + 虚拟线程，
作者报告 16.9k QPS。这个组合和我们的重合度极高，适合逐项摊开。

| 维度 | Vectra-Core | 本项目 | 谁更强 |
|---|---|---|---|
| HNSW 实现 | 有 | 有（扁平数组 + SIMD，10 万点 104.5 µs） | 接近 |
| SQ8 量化 | 有 | 有（内存 3.35×，召回 0.9983→0.9150） | 接近，但我们**记录了代价** |
| 元数据过滤 | 有（filter 表达式） | **没有**（只有 mode / rerank 两个开关） | **对方强** |
| 虚拟线程 | 用虚拟线程做并发 | 没用（Spring MVC + 线程池） | 对方更新潮，但**在本项目里不是瓶颈** |
| 稀疏检索 / BM25 | 没有 | 有（中英混合、无词典二元组分词） | **我们强** |
| 混合召回 (RRF) | 没有 | 有（向量 / BM25 / 混合三路可切换） | **我们强** |
| Cross-Encoder 精排 | 没有 | 有（MRR +9~14%，延迟 43→599 ms 的代价也写明） | **我们强** |
| 中文支持 | 无 | 端到端（分词、BGE-small-zh、中文语料） | **我们强** |
| 持久化 | 未提及 | 二进制快照，冷启动 113 s → 173 ms | **我们强** |
| 基准报告 | 只有 QPS 一个数 | 五节 + 对照实验 + 失败记录 | **我们强** |
| 代码规模 | 未统计 | Java 12,503 行 / Python 3,360 行 | — |

**结论：** 在"索引内核"这一层我们打平；对方的元数据过滤我们确实没有；
但在"一条检索链路是否完整"上（稀疏 + 稠密 + 融合 + 精排 + 持久化）我们是完整的那一方。

## 三、与 jvector 对比（差距在哪）

jvector 是 Lucene 级别人的作品，拿它当参照不是为了比赢，而是为了知道自己离"工业级"差几步。

| 维度 | jvector | 本项目 |
|---|---|---|
| 索引 | 内存 HNSW + **磁盘索引**（可加载超内存数据集） | 纯内存（10 万点约 219 MB 快照） |
| 量化 | PQ / BQ / Fused ADC，**int8 SIMD 点积** | SQ8，解码成 float 再算 |
| 更新 | 增量插入 + 后台压实 | 增量插入 + 手动压实 |
| 过滤 | 与索引融合的过滤 | 无 |
| 规模 | 十亿级验证过 | 十万级实测 |
| 我们的位置 | — | 大约差一个数量级的工作量 |

## 四、我们的真实优势（都是可验证的，不是形容词）

1. **每个优化都有对照实验，包括失败的那些。**
   - 堆外内存：查了资料**否决**，理由写进设计取舍 8（JDK 21 外存 API 仍是预览）。
   - StampedLock 乐观读：先测了锁开销——无竞争 16 ns，占 104 µs 检索的 **0.015%**，**否决**。
   - SQ8：第一版 recall 在 2 万点验证集上从 1.0000 掉到 0.6567，定位到"固定刻度 127 浪费了 96% 的量化格"，
     改成按维度取满量程后 10 万点正式测回到 0.9150。
   一个只会说"我做了 A、B、C"的简历，比不过一个能说"我否掉了 A 和 B，因为量出来只有 0.015%"的。

2. **混合检索那组"反直觉"的评测结论。**
   自建评测集上纯 BM25 的 R@10 是 0.9611，混合只有 0.9472 —— **混合更差**。
   原因写清楚了：等权 RRF 假设两路可信度相当，而自建查询集全是词面匹配，
   BM25 本来就该赢。这比"混合一定更好"的结论有价值得多。

3. **双进程切分的量化依据。**
   "编码 131 ms、检索 34 ms，端到端 166 ms"——瓶颈在跨进程编码而不是索引本身，
   所以调 HNSW 参数是南辕北辙。这个判断是做基准做出来的，不是猜的。

4. **文档密度。** 12 条设计取舍、13 个面试问答、一份带"失败与局限"的基准报告、
   一张可交互架构图。这份产出在同类个人项目里不常见。

## 五、我们的真实劣势（不掩饰）

1. **SQ8 只有内存收益，没有速度收益。** 实测延迟 **×1.40**（68.7 → 96.1 µs），建图 2.5 倍。
   根因很明确：我们把 int8 解码回 float 再算点积，带宽省下来了但多了一次转换。
   真正要快得用 int8 点积内核（AVX2 的 `dpbusd` / Vector API 的 int8 通道），
   **这一步没做，本项目的 SQ8 是"容量优化"而不是"性能优化"。**
2. **没有元数据过滤。** Vectra-Core 有，jvector 更成熟。这是最容易补、也最显眼的一块。
3. **召回评测用合成数据。** 高斯混合簇 + 已知项检索，能测出参数趋势，
   但换成真实中文语料（BEIR-zh 之类）结论可能变化，这一点在报告里写明了。
4. **规模只有 10 万。** 百万级只有理论推算（建图 151 s → 几分钟），没实测。
5. **并发数字不可用。** i7-14650HX 是 8 P + 8 E 混合架构，同配置跑五次得到
   20k~82k ops/s 的 4 倍散布，所以任何并发数字都不进简历。

## 六、定位结论

这个项目**不是**"再造一个 jvector"，也**不是**"又一个 RAG Demo"。

它是一个**把"为什么"讲清楚的检索系统样本**：内核自己写、每步有对照、
失败也记录、边界明说。面试时能被追问三层而不塌，这就是它的价值。

如果要一句话概括差异：

> 别人证明"我的检索很快"，我证明"我知道它为什么快、什么时候不快、以及怎么量出来"。

## 七、下一步（按性价比排序）

| 优先级 | 事项 | 理由 |
|---|---|---|
| 高 | int8 点积内核 | 让 SQ8 从"省内存"变成"又快又省"，现有工作才完整 |
| 高 | 元数据过滤（`field=value` 表达式） | 与 Vectra-Core 最直接的短板，工作量可控 |
| 中 | 真实中文评测集 | 替换合成数据，让召回结论经得起追问 |
| 低 | 磁盘索引 | 工作量是前几项之和，属于另一个量级 |
